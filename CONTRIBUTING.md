## Repository Workflow Standards ##
The repository workflow will follow an order similar to or exactly like this. 
Issue -> Create Branch -> Make Changes -> Commit -> Push -> Pull Request -> Code Review -> Merge
It is important to maintain an order for several reasons, we will be able to document all changes efficiantly this way, squashing bugs will be made easier as well because the exact changes will be noted. 

## Branch Naming Conventions ##
Branches should be quick, simplified, all lowercase descriptions what the branch is<br>


## Pull Request Procedures ##
Pull Requests will leave in detail what is being changed/added why and completion status<br>
Pull Requests will allways be reviewed and tested by other contributers<br>
Any affected feature will be checked before Pull Request is accepted<br>
The author may merge themselves once reviewed<br>
Bugs should be noted<br>

## Code Review Requirments ##
Code should follow these guidelines<br>
Any variable that represents something will be named accordingly with a single capital letter<br>
"main()" will allways be the bottom most funciton<br>
Classes,Functions, loops, ifs, should be indented<br> 
Any Comments are not redundant and actualy provide usefull information <br>
Code is readable and maintainable <br>
Tests have been added/removed when appropriate <br>
Existing functionality isn't broken <br>
Documentation is updated <br>



## Commit Message Formats ##
Some keywords are to be used to lable Commit messages <br> <br>

 feat: New feature <br>
 fix: Bug fix <br>
 docs:Documentation <br>
 refactor: Code restructuring <br>
 test: Tests <br>
 chore: Maintenance/configuration <br> <br>

 Commit messages should also provide a description of the change if possible code line numbers for key areas
